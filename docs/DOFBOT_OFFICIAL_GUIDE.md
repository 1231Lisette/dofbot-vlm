# DOFBOT Jetson Nano 官方资料学习总结与安全上手指南

> 状态：基于官方资料和当前 Jetson 的只读检查整理；不代表已经完成真机验收。
>
> 最后核对：2026-09-26。
>
> 当前硬件状态：舵机总线线束发生断线事故，舵机与主控板已经物理断开。更换并核对线束前，不得恢复舵机供电。

## 1. 资料范围与结论

本总结核对了以下官方来源：

- [Yahboom DOFBOT Jetson Nano 官方 GitHub](https://github.com/YahboomTechnology/dofbot-jetson_nano)，核对提交 `b99be3c177c516476d28264cdd38f5813ab630fe`（2026-07-28）。
- [Yahboom DOFBOT Jetson Nano 官方教程站](https://www.yahboom.net/study/Dofbot-Jetson_nano)。
- GitHub 仓库内 439 份 PDF 的全文索引；精读了首次试用、扩展板、接线、校准、后台服务、Jupyter、基础舵机控制、动作组、ROS/MoveIt 真机控制、系统备份和故障处理材料。
- 当前 Jetson 原厂目录 `/home/jetson/Dofbot`、`Arm_Lib 0.0.5`、相关 Notebook、ROS 工作区和服务配置的只读检查。

官方资料覆盖从首次试用到视觉、语音、ROS 和 MoveIt 的完整演示链，但它更像教学案例集合，不是工业级安全手册。部分教程鼓励“Run All”，而同一个 Notebook 后半段可能包含运动、无限循环、动作组回放或永久参数写入。真机接入必须在官方步骤之外增加物理断电、单控制者、逐关节标定、软限位和故障状态设计。

## 2. 首先区分两代软件环境

官方仓库同时包含旧版和新版资料，不能混用命令。

| 项目 | 当前这台 Jetson | 官方较新 `DOFBOT_AI` 教程 |
|---|---|---|
| 系统 | Ubuntu 18.04.6 / L4T R32.4.4 | 主机加 Docker 的组合环境 |
| ROS | ROS 1 Melodic | Docker 内 ROS 2 Humble 为主 |
| 舵机库 | `Arm_Lib 0.0.5` | 仍可见 `Arm_Lib`，另有新版 ROS 2 驱动 |
| 控制链 | Jetson I²C bus 1 -> 扩展板 `0x15` -> 串行总线舵机 | Docker/ROS 2 节点 -> 驱动 -> 扩展板/舵机 |
| 教程代码位置 | `/home/jetson/Dofbot/...` | Docker 内 `/root/Dofbot/...`、`/root/dofbot_ws/...` |
| Jupyter | 主机 `IP:8888` | Docker 常用 `IP:9999` |

针对当前机器，应以 Jetson 本机的 `Arm_Lib 0.0.5` 和 `/home/jetson/Dofbot` 为基线。未经完整迁移和备份，不执行新版教程中的 Docker、ROS 2、固件刷新或系统升级步骤。

## 3. 硬件控制链与实体按键

官方资料说明：扩展板支持多种主控，但同一时刻只能由一个主控连接和控制。总线舵机接口允许多个舵机级联，因此一根线损坏并不必然意味着所有关节立刻失去电源或停止保持；实际结果取决于断的是电源、地、通信线还是机械结构被其他关节带动。

扩展板关键按键：

| 按键 | 官方定义 | 安全含义 |
|---|---|---|
| K1，默认模式单击 | 总线舵机复位，机械臂回到直立姿态 | **会运动，不是安全键** |
| K1，默认模式双击 | 快速复位舵机 | **可能高速运动，禁止在调试时误触** |
| K1，学习模式 | 记录当前姿态 | 会把姿态写入动作组 |
| K2，短按 | 总线舵机紧急停止、关闭扭矩 | 是厂商提供的实体卸力手段，但不能代替切断电源 |
| K2，长按约 10-15 秒 | 切换底层 MCU BootLoader | 不是日常急停操作，不能长按试验 |
| RESET | 重启协处理器/相关控制器 | 可能改变控制状态，不等于安全停机 |

第一次真机试验必须另外准备能够直接切断舵机电源的实体手段。SSH、关闭 Notebook、`Ctrl+C`、K2 和软件“急停”都不应作为唯一保护。

## 4. 官方推荐的上手主线

官方期望用户按以下顺序体验：

1. 检查硬件安装和接线。
2. 上电，等待原厂启动程序和提示音。
3. 使用 YahboomRobot App 连接设备。
4. 检查机械臂中位；必要时校准舵机中位。
5. 校准相机颜色/视觉偏差。
6. 管理或关闭原厂 App 控制程序，避免它与示例争用控制通道。
7. 通过 Jupyter 学习 RGB、蜂鸣器、单舵机、角度读取和多舵机控制。
8. 再进入动作组、抓取、视觉跟踪、ROS 和 MoveIt。

这条路线适合一台机械、电气和出厂参数都正常的设备。当前设备已经发生线束损坏，不能直接从第 2 步继续，必须先执行本文第 9 节的分阶段验收。

## 5. `Arm_Lib 0.0.5` 的实际行为

### 5.1 初始化与退出

```python
Arm = Arm_Device()
```

当前库的构造函数只会打开 I²C bus 1，并设置扩展板地址 `0x15`；代码中没有自动调用 `Arm_serial_set_torque(1)`。

```python
del Arm
```

只会丢弃 Python 对象。库中没有“对象销毁时自动关闭扭矩”的安全逻辑，因此退出程序后，舵机仍可能保持最后目标。

### 5.2 关节编号和厂商角度定义

官方定义从底座向末端编号：

| 舵机 ID | 位置 | 厂商 API 范围 | 库内方向处理 |
|---|---|---:|---|
| 1 | 底座 | 0-180° | 正向 |
| 2 | 肩部 | 0-180° | 软件反向 |
| 3 | 肘部 | 0-180° | 软件反向 |
| 4 | 腕部俯仰 | 0-180° | 软件反向 |
| 5 | 腕部旋转 | 0-270° | 特殊 270° 换算 |
| 6 | 夹爪 | 0-180° | 正向 |

这些是驱动接受范围，不是本机已经验证的机械安全范围。自己的程序必须使用更窄、经过实测的软限位。

### 5.3 API 风险分级

| API | 官方用途 | 风险与限制 |
|---|---|---|
| `Arm_serial_servo_write(id, angle, time)` | 单舵机运动 | 直接运动；`time=0` 是最快速度 |
| `Arm_serial_servo_write6(...)` | 六舵机同时运动 | 高风险；会把未知姿态拉向目标 |
| `Arm_serial_servo_read(id)` | 读取角度 | 名义为读取，但底层仍先写查询寄存器；不能视为电气零影响 |
| `Arm_ping_servo(id)` | 探测舵机 | 同样向控制板写查询寄存器 |
| `Arm_serial_set_torque(0)` | 关闭扭矩 | 机械臂可能因重力下坠；必须先支撑连杆 |
| `Arm_serial_set_torque(1)` | 打开扭矩并保持姿态 | 若目标与实际姿态不同，可能突然纠偏 |
| `Arm_serial_set_id(id)` | 改总线舵机 ID | 永久配置风险；只能在明确隔离单个舵机时使用 |
| `Arm_serial_servo_write_offset_switch(id)` | 保存中位偏移 | 永久标定风险；不可用于一般测试 |
| `Arm_Button_Mode(1)` | 进入学习模式 | 自动关闭扭矩，机械臂可能下坠 |
| `Arm_Button_Mode(0)` | 退出学习模式 | 官方说明会重新打开扭矩 |
| `Arm_Action_Mode(1/2)` | 单次/循环播放动作组 | 不知道已存动作时禁止使用 |
| `Arm_Action_Mode(0)` | 停止动作组 | 只停止回放，不等同于切断舵机电源 |
| `Arm_Clear_Action()` | 清空动作组 | 不可恢复的数据修改 |
| `Arm_reset()` | 重启驱动板 | 状态变化不可按“只读”处理 |

官方的扭矩定义可参见[中位调整说明](https://www.yahboom.com/build.html?cid=442&id=4472)：`0` 为关闭扭矩、允许手动调整，`1` 为开启扭矩、保持目标角度。

## 6. 官方示例中必须知道的陷阱

### 6.1 单舵机示例不是小幅测试

`3.ctrl_servo.ipynb` 先把 6 号舵机写到 90°，之后在 120°、50°、120°、180°之间无限循环。它适合确认完夹爪结构后的演示，不适合作为未知机械臂的首次命令。

### 6.2 “读取舵机角度”不是全程只读

`4.read_servo.ipynb` 前半段循环读取 1-6 号舵机，后半段会先把 6 号舵机写到 150°再读取。官方 PDF 却建议运行整个 Notebook。因此不能按文件标题判断安全性，也不能使用 `Run All`。

### 6.3 全舵机示例会复位并高速扫动

`5.ctrl_all.ipynb` 会先把六个舵机全部写到 90°，随后以很短的时间参数在大范围内连续变化。当前设备禁止运行。

更重要的是，当前 Jetson 上的该 Notebook 还额外存在：

```python
Arm.Arm_serial_set_id(6)
```

当前官方 PDF 的同名示例没有这一行。其来源可能是旧镜像差异、历史修改或残留单元；在溯源前必须视为危险异常，绝对不能执行。

### 6.4 动作学习必须逐格执行

官方明确要求 `8.study_mode.ipynb` 逐格执行，不得运行全部：进入学习模式会关闭扭矩；退出学习模式会重新打开扭矩；后续单元会回放、循环回放或永久清空动作组。

### 6.5 官方标定程序也会先运动

中位标定示例会先执行六轴目标姿态，例如 `(90, 90, 90, 90, 90, 180)`，然后才关闭扭矩供手动调整。未知或受损机械臂不能把它当成首次安全卸力程序。官方也明确指出该程序只能在确实需要中位调整时逐步执行，不能随意运行。

### 6.6 夹爪堵转会烧舵机

官方特别警告：夹爪角度与物体尺寸不匹配会造成堵转和烧毁。官方给出的 3 cm 方块参考值约为 134°，但这只是原厂结构参考，不可替代本机实测的电流、温升和闭合限位。

## 7. 原厂后台程序与控制权

官方旧版教程说明，原厂镜像可能在开机后自动运行 App 控制程序，运行其他示例前应先结束它；新版教程同样警告，开机程序会干扰其他例程。

当前 Jetson 已观察到：

- `dofbot_oled.service`：OLED 状态显示，暂时保留。
- `jetson_jupyter.service`：Jupyter 服务。
- `arm.service`：启动 ROS `/kin` 运动学服务；其启动配置没有直接调用 `Arm_Lib` 舵机写入。
- 当前没有在桌面自动启动项中发现 App 控制程序，但仍需在每次真机上电前检查进程、容器、ROS 节点和 `/dev/i2c-1` 占用。

原则：同一时刻只能有一个进程拥有机械臂硬件通道。App、手柄、Notebook、ROS 驱动、动作组程序和自己的桥接服务不能并行控制。

## 8. 为什么之前手动扭动后会主动转回

最符合官方控制模型的解释是：舵机当时已经处于扭矩开启状态，并保存着一个目标角度。手动扭动制造了实际角度与目标角度的偏差，闭环控制随后主动纠偏。

不能据此断言刚才有人调用了 `Arm_serial_set_torque(1)`：

- 此前没有显式调用该 API。
- `Arm_Device()` 本身不会开启扭矩。
- 扭矩可能来自上电默认状态、先前程序、退出学习模式、动作组或扩展板保留状态。
- 此前执行过的版本/读取/探测 API 会写查询寄存器，因此不能声称对控制板完全无影响；但它们不是显式角度或扭矩命令。

## 9. 针对当前设备的安全验收流程

每一阶段都是门禁；前一阶段未通过，不进入下一阶段。

### 阶段 A：事故隔离和物理修复

- 保持舵机线与主控板断开，并断开舵机电源。
- 拍摄损坏线束、两端插头、线芯颜色和所在关节。
- 更换损坏线束，不采用临时绞接加胶带后上电的方式。
- 检查裸铜、短路、焦黑、异味、弯针、松脱、舵盘和支架变形。
- 确认线序、电源极性和插头方向；断电测量电源对地没有短路。
- 不确定时交由实验室硬件人员或 Yahboom 支持确认。

### 阶段 B：舵机断开，仅验收 Jetson

- 制作并验证原厂系统盘完整镜像备份。
- 记录系统、ROS、Python、CUDA、`Arm_Lib` 和扩展板固件版本。
- 盘点 systemd、桌面自启、Docker、ROS、Jupyter、App 和手柄进程。
- 确认哪个进程能访问 `/dev/i2c-1`，建立唯一所有者规则。
- 不升级系统、不刷新扩展板固件、不覆盖原厂镜像。

### 阶段 C：建立可控上电环境

- 将机械臂固定在稳定桌面，并支撑所有会因卸力下坠的连杆。
- 清空运动范围，移除相机线、舵机线等可能被缠绕的物品。
- 准备随手可操作的舵机电源切断装置。
- 最好使用带限流或保险的电源，并从低风险负载开始。
- 确认 K1 不会被误触，明确 K2 短按位置，但仍以断电为最终急停。
- 禁止 App、手柄、Notebook、动作组和自有程序同时运行。

### 阶段 D：逐个识别舵机

- 一次只连接或隔离验证一个舵机；不先连接六轴同时试验。
- 先确认实体关节、线束路径和预期 ID，不调用改 ID API。
- 关节卸载或可靠支撑后才进行带电观察。
- 任何上电即冲转、嗡鸣、异常发热、读数跳变或多舵机联动，立即物理断电。
- 读取和探测也只在确认控制板协议及现场保护后执行。

### 阶段 E：逐关节小幅运动与标定

- 从当前实测角附近的 1-2°变化开始，采用较长运动时间。
- 分别确认 ID、实际运动方向、读回值、重复性和掉线行为。
- 逐步确定机械软限位；不触碰厂商 API 的理论满量程端点。
- 记录零位偏移，但未经专门标定流程不写入中位偏移。
- 对夹爪额外记录物体尺寸、目标角度、电流、温升和堵转迹象。

### 阶段 F：联合运动

- 六个舵机全部单独通过后，先做两关节低速测试。
- 再验证一个经过人工检查的安全姿态。
- 不使用舞蹈、随机 MoveIt、全范围扫描和未知动作组作为联合测试。
- 机械安全验收完成后，才进行相机外参、桌面平面和抓取偏差标定。

## 10. 过渡到自己的程序

自有系统应保留项目现有 `RobotInterface` 边界，并增加一个 Jetson 侧单一硬件桥。推荐链路：

```text
本地规划/视觉
  -> 受约束的网络命令
  -> Jetson 唯一硬件桥
  -> 关节名/ID/方向/零偏/限位映射
  -> Arm_Lib
  -> 扩展板 0x15
  -> 总线舵机
```

硬件桥最低要求：

- 启动默认不运动，不自动回中，不自动打开动作组。
- 显式 `enable` 后才接受运动命令。
- 单进程锁，拒绝第二控制者。
- 明确区分诊断、状态变化、运动和永久配置 API。
- 每个关节使用实测 ID、方向、零位和软限位。
- MuJoCo 弧度不能直接传给真实舵机。
- 限制位置、速度、加速度、命令频率和单步变化量。
- 拒绝 NaN、无穷、越界、时间戳过期和序列错误命令。
- 网络超时进入经过真机验证的安全状态。
- 记录每一条实际下发命令、来源、映射结果和响应。
- 退出程序时的行为必须显式设计；不能依赖 `del Arm`。
- 软件急停、K2 卸力和物理断电分别建模，不能混为一个状态。

推荐验证顺序：

```text
纯函数映射测试
-> shadow mode（只记录、不下发）
-> 仿真回归
-> 单关节 1-2°低速测试
-> 六关节逐个验收
-> 两关节协调
-> 人工确认的安全姿态
-> 网络超时/重复命令/断连测试
-> 视觉与抓取
```

## 11. ROS 和 MoveIt 的正确定位

官方 ROS 示例会启动真机控制节点，并在收到 `/TargetAngle` 等消息后直接调用单舵机或六舵机写入函数；示例甚至会把相同命令重复发送两次。启动节点本身也可能移动到预设位置，因此不能把“只是启动 ROS 节点”视为无运动操作。

官方 MoveIt 真机教程通过订阅关节状态/轨迹并转换为真实舵机控制，明确提醒真实机械臂没有障碍规避保证，推荐使用预设姿态。对本项目而言，MoveIt 应在完成真实关节映射、软限位、碰撞模型和硬件桥之后接入，不应直接连接原厂示例驱动。

## 12. 当前禁止事项

在线束修复和阶段 A-C 完成前：

- 不给舵机总线供电。
- 不运行任何 `Arm_Lib` 方法，包括所谓读取或探测。
- 不按 K1，不长按 K2，不按 RESET 试验。
- 不运行 Jupyter 的 `Run All`。
- 不运行 `ctrl_all`、`left_right`、`dance`、动作组、抓取或 MoveIt 真机示例。
- 不调用 `set_id`、中位偏移、清空动作组、复位或固件升级接口。
- 不升级 Jetson 系统或覆盖原厂镜像。

## 13. 恢复前仍需确认的问题

- 损坏的是哪根线、哪一股导体、对应哪个舵机和哪一侧接口。
- 六个舵机的实际 ID 是否仍为 1-6，是否存在重复 ID。
- 当前线束级联拓扑和每根线的电源/地/信号定义。
- 扩展板固件版本 `0.2` 对应的准确协议和上电扭矩默认值。
- 当前 Jetson Notebook 中额外 `Arm_serial_set_id(6)` 的来源。
- K2 短按在当前固件上的实际行为，以及断电重启后的扭矩状态。
- 舵机断开通信但保持供电时，是保持上次目标、卸力还是进入其他状态。
- 每个真实关节的安全限位、零位、方向、最大速度和可接受温升。
